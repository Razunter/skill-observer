## 1. Find candidates

Start with the active branch, including completed work, and use the digest as an index, not a whitelist. Read the signals, corrections, observations and User note. If a finding or dismissal depends on clipped or compacted evidence, recover the original request, reply, call or result. In the active branch's saved session file, start at the supplied leaf ID and follow each returned `parentId`. Use `read` to query only known IDs, for example `saved-session.jsonl?q=select(.id == "ENTRY_ID" and .type != "session")&compact=true`. If a row is missing, ambiguous or clipped, report the source gap instead of substituting a sibling row. If the branch lacks the source, use a narrow archive search for the named session or lead in this project, if available. Cite the decisive quote and source locator with the finding. If you cannot recover enough primary evidence, name the gap and do not present the lead as verified.

Stop when the original request was answered and the branch supplies no concrete lead, correction or new User note. Even after a correct answer, treat a failed lookup the user reports in named sources as a concrete lead, check only those sources against the source that answered the question, and report the smallest verified next action. Do not turn a source-supported answer into an audit of files or behavior that the original work did not need.

Skill findings include:

- **Improve**: the agent broke a rule a loaded skill documents; a user correction exposes a missing rule or edge case; a tool error in a turn with a skill loaded traces back to that skill's method; a better workflow emerged than the skill recommends; a skill's assumption proved wrong; new tooling made a step obsolete.
- **Simplify**: two rules contradict each other; the agent keeps failing a rule, which then becomes a barrier or goes.
- **New skill**: a multi-step workflow done by hand that no skill covers, visible as similar tool outlines across turns; a method the user explained ("I always do it this way").

**Check the current checkout before choosing a remedy.** Follow the evidence to the affected code, tests, docs or configuration; check what the existing check actually covers and whether its hook or CI wiring runs it. Repair an existing broken or unwired check rather than adding a parallel one. If production code is now correct but the old failure would still pass the suite, propose the smallest regression test in that suite, with the known bad behavior it must catch and the legitimate case it must preserve. For a navigation fix, name the exact page to edit and the source it should point to. A judgment problem gets review guidance. Treat access to information as a permission request, not authority to read a service or credentials.

**Remedy ladder.** Rank by cost, not owner: configuration or wiring repair, text or skill edit, amendment, barrier rule, pattern amendment, project check, then checked hook or owned extension changes. Leave a tool unchanged when it rightly rejects misuse. A supplier label names a tool's supplier, not the cause. Weigh caller error, configuration, another extension's interception and unknown causes. Read owners' docs or source only where evidence points.

**Report items.** If no proposal fits or the destination, owner tool or necessary check is unavailable or denied, report the finding without an Ask or ledger decision. Give the owner, request and result, expected behavior with its source, cause (confirmed, suspected or unknown), a check with a legitimate counterpart, and the next action. For missing capabilities, name the needed API, state owner, benefit and risks. Mark missing facts unknown.
