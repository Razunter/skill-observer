# Development and implementation reference

For installation, see [Setup](setup.md). For the user-facing observation pass and session digest, see [Observation](observation.md). For amendment storage, delivery, staleness and replay, see [Amendments](amendments.md). The [README](../README.md) gives the extension overview.

## Advisory proposal selection

`observer_review` is activated with the other observer tools on the first explicit pass. Prepare canonicalizes project/global identities, merges duplicate evidence and removes prior scoped declines. Each candidate carries its exact change. For an observer-owned rule or reference mutation (on-read append, pattern amendment or barrier rule, stale Update/Delete, withdrawal, compaction), Prepare builds the operation `observer_resolve` would carry out: the rule identity, the trimmed body, section or samples it would write, the reference files it would write or delete, the rule and reference bytes it read itself (as SHA-256), and a deterministic preview rendered from that operation. It refuses a change whose preview holds a carriage return, since native Ask shows CRLF as LF and a bare CR as a space, so the user would approve bytes other than those written; a stale Keep, which writes no new content, is not prepared and keeps a file's CRLF line ends. A deletion of a skill's last on-read amendment holds the skill's reference folder as Prepare read it, even when empty. A direct edit of a local, managed, new or project target keeps the pass's own exact preview and its normal owner. Each eligible proposal comes with a reference `{ reviewToolCallId, candidateId, contentHash }`; the successful Prepare result on the session branch is the only record of it. Prepare returns minimized `judgeStates` and `needsRanking: true` only for the priority class crossing the five-question cutoff, and only with an explicitly assigned, available host `judge` model. A class is compared only when it has some slots available but more eligible candidates than those slots; fully selected and fully deferred classes need no ranking. Exact previews and full transcripts are not ranking inputs.

Active tools belong to the running process, so a session that starts, switches or branches onto a branch still inside an observation pass gets the observer tools back. That lets a restored turn resolve the approvals its saved branch already holds.

Prepare drops a scoped decline once its identity is known and before it validates or reads that proposal's target, so a declined proposal whose skill was removed or whose target is no longer writable does not fail the call. A stale amendment's Update and Delete drafts form one proposal holding both as `alternatives`, each with its own prepared change and preview; that Keep/Update/Delete question takes one of the five slots. An on-read append whose section the amendment already holds verbatim is prepared with effect `record` and previewed as a ledger-only change, since publication leaves the file as it is. A compaction's `includes` resolve to the fingerprints of the on-read appends prepared in the same call, so a re-offered Later fix with a reworded gist keeps its recorded identity at `observer_resolve`; an inclusion that names no such append, or more than one, fails Prepare.

Select takes only those references. It resolves each through the branch's strict completed-call lookup to a successful `observer_review` Prepare, requires exactly one saved proposal with that candidate ID, and rejects a duplicated reference, a content hash that differs from the saved proposal, or a saved proposal that no longer matches its own hash. It accepts no candidate drafts, so a changed proposal is prepared again. Neither action writes a file or authorizes one. During a pass, both outputs carry their own `observerToolCallId`, which an approval cites.

The gate reads the effective explicit assignment through `pi.pi.settings.getModelRole("judge")`, then uses the host's exported `resolveScopedModels` helper against authenticated `ctx.modelRegistry.getAvailable("all")` models of kind chat, tiny or judge, with discovery disabled. The installed host's `judge_batch` uses the `judge` role, not `decision`; generic role resolution can select built-in defaults without an explicit assignment, while `ctx.models.resolve` only sees chat models and misses native judges. Missing configuration, unavailable models, unreadable settings or missing host APIs mean no ranking request and empty `judgeStates`. Select rechecks this gate and ignores caller-supplied rankings when unavailable, returning one truthful fallback explanation for compared classes.

With that gate open, the pass may use one installed host `judge_batch` with a shared ordinal evidence/impact/recurrence rubric and no retry. No provider client is added, no new settings are enabled, and no ranking/model call occurs inside the extension tool. A class outside that cutoff comparison, including a singleton, needs no judge or fallback disclosure. If judge support/model use is unavailable, a batch fails, answers are missing/invalid, confidence is below 0.7 or scores contradict their evidence, Select returns one fallback explanation and uses stable evidence/repeat ordering.

Selection always preserves stale Update/Delete, explicit User note, evidence-backed finding and compaction priority, with at most five questions in the main batch. An answer retracting an applied fix can require a separate prepared and selected withdrawal question in the same pass, as described in [Observation](observation.md#observe). Advisory scores reorder only within classes; they cannot resurrect declines, dismiss eligible findings, approve publication or bypass barrier replay. Overflow remains deferred: ordinary project/skill proposals are recorded as Later, while stale amendments and compactions retain existing re-offer behavior. Questions still show exact previews and combined supporting evidence, not merely a judge score.

## Proposal approval

`observer_resolve` writes an applied on-read fix, pattern amendment or barrier rule only when the saved session branch shows the user explicitly approved its prepared proposal in the current observation pass. The answer carries `approval`: the proposal's Prepare `reference`, the Select call ID and the `ask` call ID. The resolver uses them only to locate evidence, then checks, through the strict completed-call lookup, that the Prepare succeeded and still holds the proposal under its content hash, that a successful Select after it selected exactly that reference, and that a later `ask` the model made natively holds one question whose `id` is the proposal's `candidateId`, whose one `Apply` option previews the prepared `preview` unchanged, and whose answer, for those same options, is `Apply` alone. The section or rule written is the prepared one: an on-read append's section, or a rule's name, body, pattern, scope and samples, which the resolver replays before writing. The answer carries no `rule`, and its skill, kind, gist and any fingerprint must match the proposal. It is written only while the target holds the bytes Prepare read, or, for an on-read amendment, already holds the section verbatim, so the write adds nothing.

Stale Update and Delete answers and every withdrawal are guarded the same way. A stale amendment's proposal holds its prepared Update and Delete as `alternatives`; its question offers each on an `Update` or `Delete` option previewing that alternative's `preview` unchanged, beside `Keep`, and the user's selection of one alone approves that alternative only. A `stale` answer with `action: "update"` or `"delete"` carries that `approval`, and the resolver writes the alternative's body and reference files, or deletes the rule and releases its reference files, exactly as prepared. A `withdrawn` answer carries the `approval` of its prepared withdrawal, answered `Apply`, whatever the withdrawal does: only record it, delete the rule file, or rewrite the on-read amendment with the prepared body and reference files. Neither answer carries a `body`, `references` or `rule` of its own, and one that does is refused; a withdrawal the user asked for in prose is still prepared, shown and asked. Stale Keep stays outside approval: it only re-pins, and a `keep` answer carrying a `body`, `references` or `approval` is refused. The resolver writes only while the rule file and the skill's reference folder hold the bytes Prepare read. A stale Keep's re-pin of the `skillHash` line alone does not count as a change, since it adds no instruction content; any other change, such as text added to a rule after its deletion was previewed, writes nothing until the change is prepared and asked again. Stale answers and withdrawals take no reconciliation.

An applied compaction is guarded the same way. Its `compactions` entry carries the `approval` of its prepared compaction, answered `Apply`, and no `body`, `includes` or `references` of its own; one that carries any of them is refused. The resolver writes the prepared body and replaces the skill's reference folder with the prepared set, which removes the files the preview lists as deleted, and checks coverage against the prepared `includes`: the fingerprints of the on-read appends of the same Prepare it covers. It writes only while the amendment and the reference folder hold the bytes Prepare read, a re-pin aside. A compaction takes no reconciliation either: it rewrites the whole body, so it cannot keep content added after Prepare, and a changed amendment needs a new compaction and question.

A raw section or rule draft, a forged or mismatched reference, a result or text claiming consent, a hook-only or nested `ask`, a cancelled, failed, duplicated or misordered receipt, a chat redirect, a timeout default, an empty answer, any other or additional option, and custom input approve nothing. A note on `Apply` approves only with the main agent's classification: `approval.nonModifyingNote` quotes the note exactly as the `ask` result holds it and gives the agent's reason it changes nothing the preview shows. The resolver checks that the quote is that answer's note, on `Apply`; it cannot check the judgment, which the main agent owns. A modifying or ambiguous note gets no classification and needs a new proposal and question, and a classification never turns custom input, another option or an answer without a note into approval. A failed approval writes nothing and records nothing, with its reason under the call's not-recorded answers; it never becomes Later or Decline, even for a rule whose replay failed.

When the target changed after Prepare, for instance by the user's own edit, the answer writes nothing until the main agent reconciles it. A **proposal reconciliation** is a revised on-read append or rule prepared through `observer_review` in the same pass, whose candidate carries `reconciles`: the approval exactly as `observer_resolve` would cite it, how the target changed, the reason, and the agent's judgment that the revision keeps the approved intent and the target's unrelated content. Prepare checks that the cited approval still holds, that the revision makes the same operation on the same target (the same amendment, or the same rule name) for the same skill under the same ledger identity, and that the target did change; the resolver checks the same again, that the revision was prepared after the user's answer and cites exactly the answer's approval, and that the target still holds the bytes the revision read. The answer then carries `approval.revision`, the revision's reference, and the revised content is written. An append preserves the amendment's current content except for trailing whitespace, so newly added content survives. The writer trims trailing whitespace before adding the section separator. A rule write replaces the whole file, so a revised rule's body carries the new content, and the resolver replays the revised pattern and samples before writing it; a revision that fails the replay is recorded as `later` like any rule. A revision that would delete a changed amendment or rule, or rewrite one as a stale update, withdrawal or compaction, needs a new proposal and question. Whether the revision keeps the approved intent and the new content is the agent's trusted judgment, not something the code proves. The result's `approvals` (and its text) lists, per section, rule or compaction written, the user's approval, any note classification, and any reconciliation, the last named as the agent's revision, not approved by the user.

Authority comes from the branch alone; there is no approval journal or cache. The current pass starts at the latest `/observe` message and ends at a later prompt the user types, a `/skill:` start or a `/clear` reset; a new `/observe` starts another. An approval lasts while its whole chain stays on the branch inside the current pass and the user has sent no message (prompt or steering) since answering, which may retract it. Compaction, a resumed session, agent and harness messages and tool results leave it intact, so a retry in the same pass may reuse it; an already-present section is not appended twice. The resolver checks the approval and the target's bytes when it validates the call and again after the replay wait, with nothing awaited before the writes; later changes to a target within the call are its own answers'. This is trusted-host enforcement of the recorded correspondence, not a filesystem permission. Every rule and reference change `observer_resolve` makes rests on such an approval, with three exceptions that keep their own checks: a stale Keep's re-pin of the `skillHash` line, local, managed and new-skill edits, which the main agent makes with the normal tools and the resolver only records, and project publication, which the resolver validates from its write and check receipts and never writes.


## Ledger

`observer_resolve` appends one record per proposal to `<agent dir>/skill-observer/ledger.jsonl` (global, not per project): fingerprint, target skill, kind (`local`, `managed`, `upstream`, `plugin` or `new`), gist, outcome, timestamp and session id, plus `rule`, the rule file, for every answer that wrote one, and `evidence`, the quotes the question cited, each as `{ quote, count }` with the quoted signal's repeat count. An answer that cites nothing keeps the evidence last recorded under its fingerprint, so re-offering a proposal or settling its stale amendment leaves what it rests on intact. A `later` answer, skill or project, may carry `reoffer`: which observation would change the decision, when it could arrive, and whether the deferred action is still possible. The pass writes one on each `later` it records itself (past the cap, or a barrier set aside because the check can't run) and on a user's Later only from the user's own note; the tool can't tell the two apart, since a Later carries no approval. It keeps `reoffer` on `later` answers only, drops it from any other, and refuses a blank one. Proposal outcomes are `applied`, `later` or `declined`; `withdrawn` takes back an earlier applied fix (see [Withdrawals](#withdrawals)); stale-amendment answers are `kept`, `updated` or `deleted`, recorded under the fingerprint the rule carries (for a skill's on-read amendment, its own fingerprint; see [The skill's on-read amendment](amendments.md#the-skills-on-read-amendment)), and a stale delete of a skill's on-read amendment also records each fix in force in it as `deleted`. A compaction's record carries `compaction: true` (see [Compaction and reference files](amendments.md#compaction-and-reference-files)). Older ledgers also hold `merged` records, which passes before ADR 0003 wrote for an on-read amendment they folded into another; a `merged` record is no fix in force. Ordinary project and skill proposals past the cap of 5 are recorded as `later` without being asked; stale amendments and compactions keep their existing re-offer behavior. The fingerprint is a hash of the target skill and the gist with case, punctuation and spacing removed; a re-offered proposal is recorded under its earlier fingerprint, so rewording it keeps its identity. The latest record per fingerprint wins. The tool joins the model's tools at the session's first `/observe`, so sessions that never observe don't carry it. Prepare refuses a rule, section or compaction that can't be written (a rule name in use, a skill missing from the lock or of another provenance than the candidate names, an invalid pattern, scope or sample set, a barrier rule without a pattern, an on-read fix whose body doesn't open with a `## ` heading, a rule for a new skill, a reference file name that isn't a plain file name, a body with reference files that doesn't name each of them by its absolute path), so nothing can approve it. An answer the tool can't carry out (one of those, checked again at write time, an applied or withdrawn answer carrying a `rule` instead of `approval`, a stale answer carrying a `body` or `references`, a compaction carrying a `body`, `includes` or `references`, an approval that doesn't hold, an on-read fix for a skill with two or more on-read amendments, or a withdrawal that fails its checks) is reported and not recorded.

### Withdrawals

A `withdrawn` answer cites the fingerprint of a fix whose latest outcome is `applied`, `kept` or `updated`, names that fix's skill, and carries the `approval` of its prepared withdrawal (see **Proposal approval**). The withdrawal candidate names the fix by `fingerprint`; when the fix's rule still exists and is the skill's on-read amendment, it carries as `body` the amendment's new body without the fix's text: the tool rewrites the body and leaves the frontmatter as it is, and an empty body deletes the amendment and its reference files. When the fix's text sat in a reference file, the candidate also carries `references`, the complete new set, which replaces the folder's contents before the body is rewritten; without it the reference files stay. Several withdrawals from one amendment in one call carry the same body, and withdrawals are carried out before the call's additions, so a new body drafted from the file on disk keeps the sections the call adds. Any other rule file the tool deletes, but only if it carries the marker and that fingerprint. Prepare refuses a withdrawal of a hand-written rule, a rule holding another fix, an amendment holding other fixes with no new body, a fingerprint with no applied fix, a compaction's fingerprint, or another skill's fix. The resolver reports as not recorded, changing nothing, a withdrawal that would delete a rule file while other fixes in force, not withdrawn in the same call, still point at it (the result names them), and a withdrawal carrying a body for an amendment that a stale update or delete changed in the same call, since that body was drafted from the file before the stale answer. A fix whose rule is already gone, or that wrote none (an edit to a local or managed skill, which the pass reverts itself), is only recorded. The `withdrawn` record keeps the skill, kind, gist and `rule` of the fix it takes back. Moving a fix to another skill is one call with a `withdrawn` answer for the old skill and an `applied` answer for the new one. The pass asks about a fix you retract or redirect this way, whether in an answer's text or in a later message, and records it once you approve the withdrawal.

A record's `rule` is the path the file had when the record was written; ledger rows are never rewritten. A fix's rule is the one named by that path's file name, looked up in the amendments directory, then the rules directory, so the fixes of an on-read amendment that moved out of the rules directory stay attached to it.

### Publication phases and recording failures

One call's changes run in fixed phases across every skill it names: stale answers, then withdrawals, then the other answers in the order sent (on-read additions with pattern amendments and barrier rules where they fall among them), then compactions. Every pattern is replayed before the first change. A change that fails, or whose approval no longer holds, is reported and writes and records nothing; the others in the call still apply, and a later phase acts only on what earlier changes actually did, so a failed addition counts toward no compaction. The exception is a deletion that removed its rule file and then failed to delete the skill's reference folder: the deletion is listed as made, with its records, tombstones included, and the result's `cleanup` names what is left, for the pass to inspect and report without calling again. The result's `publications` lists each change the call carried out, in the order made: its `operation` (`stale-keep`, `stale-update`, `stale-delete`, `withdrawal`, `on-read-append`, `rule` or `compaction`), skill, rule file and the fingerprint its record carries. An on-read addition whose section the amendment already held verbatim changed no file and is not listed, nor is a deferred, refused or record-only answer. [`src/on-read-amendment-transitions.ts`](../src/on-read-amendment-transitions.ts) owns these phases; `observer_resolve` validates each answer, runs the replays, appends the records and reports.

Rule, amendment and reference file changes and the ledger append are separate writes; no call is a transaction. When the append fails, the call still returns what it carried out, and `recording` says, for each record in order, whether it reached the ledger: `recorded`, `unrecorded` or `unknown`, with the error. The append reads the ledger once beforehand; a failure before it starts writing leaves every record `unrecorded`. After a failed write, one read of the file settles each record: one written whole (its JSON complete, with or without its newline) is `recorded`, one cut short or not reached is `unrecorded`, and when the file can't be read or no longer starts with its earlier bytes followed by a prefix of the append, every record is `unknown`. The exception alone settles nothing. An applied change whose record didn't reach the ledger is an Unrecorded publication: the result lists it as made, never as `later`, and tells the pass to report it and leave the ledger to the user, without calling again or redoing it. A `later` or `declined` record that didn't reach the ledger, answered so or deferred by the replay or coverage check, is listed apart: it wrote nothing and keeps its outcome, unrecorded. Nothing is retried, repaired or replayed at startup.

The result text ends with `## What to do now` holding the `tool-result` paragraph of `observer.md` for each of three conditions it reports: a failed ledger append, a failed cleanup, and an answer refused because its target changed since Prepare or the reconciliation. The last is decided by type: `checkTarget` in [`src/proposal-approval.ts`](../src/proposal-approval.ts) throws `TargetChangedError`, and the resolution's `targetChanged` flag records that one reached the failures; the failure text is never matched. During a pass, the `ask` result hook in [`src/skill-observer.ts`](../src/skill-observer.ts) adds the Apply-note paragraph under the same heading when an answer selects Apply with a note or custom input. `toolResultGuidance` reads the paragraphs from `observer.md` on each call, so they keep a single source.

`/observe` adds the ledger to its message: deferred proposals, which the pass offers again, each with its fingerprint and, when its record has one, its `reoffer` as `Re-offer when: …`. Declined proposals are left out because Prepare already drops a scoped decline. A withdrawn fix is not listed, and neither is a compaction.

### Project-local decisions

The same ledger also stores project answers as `kind: "project"` with `target: { scope: "project", root, path, mechanism }`, without a skill name or rule path. The project root is the canonical current working directory supplied by OMP, not a discovered Git root or a caller-selected directory. Launch from the intended project directory. Project fingerprints hash an unambiguous tuple of the project namespace, canonical root, canonical root-relative target and mechanism normalized by removing case, punctuation and spacing; historical global fingerprints are unchanged. Symlink aliases of a root or target share an identity. Targets must be file paths below that root; traversal, absolute paths, dangling symlinks and symlink escapes are refused. Safe missing leaf files and directories are permitted for proposed new files.

`/observe` receives global decisions plus only the current project's decisions. Project rows never participate in skill Rules in force, compaction, stale-amendment ownership, or skill withdrawal. Earlier evidence is carried forward when a new answer does not cite evidence. Project answers offer `applied`, `later` or `declined`; they cannot carry a skill amendment.

Project publication uses normal `write` or `edit` tools, not the rule writer. An applied answer needs `publication: { writeToolCallId, checkToolCallIds, afterHash }`: the successful write/edit and subsequent successful foreground `bash` checks must be present on the actual current OMP session branch. The write must target this canonical file; each check must use an explicit `cwd` equal to the canonical project root. `afterHash` is the SHA-256 of the file's current bytes. Native hashline edit receipts and structured path-based edits are supported; delete/rename receipts and background/service checks are not. OMP's successful foreground bash results omit `exitCode`; nonzero exit codes, errors, timeouts and unfinished jobs are refused. Missing or invalid observations record no applied outcome.

During an active observation turn, successful `ask`, `edit`, `write`, `manage_skill` and `bash` outputs retain their original content/details and append `{"observerToolCallId":"<actual opaque host ID>"}` for exact review and publication receipts. Copy that exact value, rather than a file snapshot tag, command string or session-entry ID. Errors and ordinary turns keep their outputs unchanged. An exposed ID is only call metadata; the resolver still requires matching successful branch evidence and rejects unfinished/background checks.

Nested `eval` calls retain branch-local hook receipts for their actual tool arguments, completion and result details; IDs or JSON printed by eval are not receipts. Multi-file edits are accepted for each included target only after every path passes canonical project containment. An absent Bash service name can be omitted or `null`; named services remain rejected.

The extension's tool hooks save a copy of every call they see, native or not: the model's assistant message reaches the branch only after a call's `tool_call` hooks, so a copy is never dropped as redundant there. An outcome is copied only when its call was. The resolver prefers a complete native pair while rejecting duplicate IDs within either source and conflicting receipt status. Hook receipts require unchanged execution input from the result hook. A missing or revised input leaves publication unaccepted; the write must be reconciled rather than reported as applied.

Project receipts validate ledger scope and observed tool evidence; they do not attest that a successful command proves the remedy correct. These checks are trusted-host checks, not an OS sandbox or an atomic filesystem transaction. Reconcile unknown outcomes rather than inventing applied receipts.

## Extension entry

OMP loads [`src/skill-observer.ts`](../src/skill-observer.ts) through the `omp.extensions` entry in [`package.json`](../package.json). The extension has no runtime dependencies. OMP names an extension after its entry file, or after the entry's folder when the file is `index.ts`. The `skill-observer.ts` entry gives this module the name `skill-observer` and the settings ID `extension-module:skill-observer`; an entry at `src/index.ts` would instead be named `src`. Configured module paths are deduplicated by real file path, so a symlink and its target load once.

## Develop

Run these commands from a source checkout's extension root, the directory containing `package.json`. Package tarballs omit tests and development configuration.

```sh
bun install
SKILL_OBSERVER_NATIVE_TESTS=0 bun run test
bun run typecheck
```

This runs ordinary tests without launching the native OMP checks. See [Testing](#testing) for explicit native checks.

### Instruction fragments

[`observer.md`](../observer.md) is the one maintained source of the pass instructions. Gate markers in it name the evidence a part needs (see [Observation payload](observation.md#observation-payload)):

```md
<!-- when: stale -->
- **Stale amendment**: pick your verdict. …
<!-- end -->
```

A marker sits alone on its line and wraps whole paragraphs or whole list items, never part of a sentence or item. Gates are `stale`, `compaction`, `project`, `withdrawal`, `ranking`, `note` and `tool-result`; blocks don't nest. One parser, `parseFragments` in [`src/payload.ts`](../src/payload.ts), splits the file at its `##` headings and markers and throws on an unknown gate, an unbalanced or nested marker, or a block that splits a paragraph or list item. `/observe` runs it on every pass, so a malformed marker stops the pass with an error notice.

After editing `observer.md`, regenerate the committed fragment files:

```sh
bun run generate
```

It writes `observer/<section>-<gate|core>-<n>.md`, one file per fragment, where `n` is the fragment's position in its section, so a reader can browse the gated parts. `/observe` assembles from `observer.md` itself, not from these files, so an approved edit to `observer.md` applies to the next pass without regenerating. A test in `test/payload.test.ts` regenerates the files in memory and fails when `observer/` differs.

### Package a local tarball

```sh
bun pm pack
```

Run this from the source checkout's extension root. It creates `skill-observer-0.1.0.tgz` using the `files` allowlist in `package.json`: runtime source, `observer.md` and its generated `observer/` fragments, reader documentation, the licence and third-party notices, the README, and changelog. It excludes tests, development configuration, and installed dependencies. Packing creates a local archive for distribution checks; it does not publish the package. Normal setup uses a Git checkout.

### Testing

`test/setup.ts` points `PI_CODING_AGENT_DIR` at a temp dir for the whole suite, so no test or spawned `omp` reaches the live agent dir.

When the installed Bun provides the native checker, `bun check` uses the same project configuration without emitting files. The `typecheck` script remains `tsc --noEmit` for compatibility; see [Bun's checker documentation](https://bun.com/docs/runtime/check).

Tests cover digest/provenance, observer selection and publication, and amendment delivery through the extension's hooks. Prompt assertions check identities, evidence, counts and required markers rather than explanatory sentences.

Unit tests create their own temporary skills, lockfile, managed directory and plugin registry. Historical names such as `ce-commit-jj` identify fixture files, not dependencies on your installed local skills. Filesystem and subprocess fixtures do not establish model gain or effective instruction-loading parity.

### Explicit native checks

Native checks require Bun and an installed `omp` that responds successfully to `omp --version`. With `SKILL_OBSERVER_NATIVE_TESTS` unset or set to a value other than `0`, the suite enables its OMP-backed tests when that binary is available. To request those checks explicitly, run this from the extension root:

```sh
SKILL_OBSERVER_NATIVE_TESTS=1 bun run test
```

`test/native-schema.ts` is loaded by the installed OMP host without a model prompt to verify actual tool-schema registration, under a temp agent dir so the extension's startup migration never touches your rules. The amendment/replay suites use `omp ttsr test` for native trigger checks. These OMP-backed checks are skipped when OMP is unavailable or `SKILL_OBSERVER_NATIVE_TESTS=0`; requesting them with `1` does not turn a missing prerequisite into a passing check.

The `/skill:` reminder finds the skill by the first line of OMP's user-invocation template. One test renders `src/prompts/skills/user-invocation.md` from the package of the first `omp` on `PATH` (an npm or Bun global install), so a reworded template in the installed OMP fails the suite. It is skipped, independently of the native-test flag, when `omp` is missing or is a compiled binary that ships no template. Native checks still require their OMP or Bun prerequisites.

### Pre-commit hook

Enable the bundled hook in each clone with `git config core.hooksPath hooks`. It rejects unstaged or untracked files so verification matches the index, sets `SKILL_OBSERVER_NATIVE_TESTS=0` so native OMP checks stay explicit-only, and runs `bun run check` (typecheck, then tests). Missing Bun/dependencies or a failing check blocks the commit.
